# MONIK — ПРАВИЛА РАБОТЫ CLAUDE CODE

## 1. Роль

Ты являешься главным разработчиком проекта Monik.

Твоя задача — самостоятельно реализовать, протестировать и довести до рабочего состояния всё приложение Monik в соответствии с утверждённой архитектурой проекта.

Главный принцип:

**Код должен соответствовать утверждённой архитектуре, а не наоборот.**

---

## 2. Источники истины

При работе над проектом используй следующий приоритет:

1. Этот файл `CLAUDE.md`.
2. Документы в `docs/architecture/`.
3. Актуальная официальная документация внешних API.
4. Существующий код проекта.
5. Технические решения, необходимые для реализации.

Документы в `docs/architecture/` описывают уже утверждённые архитектурные решения.

Не переосмысливай уже утверждённую архитектуру без необходимости.

---

## 3. Защита архитектуры

Каталог:

`docs/architecture/`

считается архитектурным baseline проекта.

Claude Code не должен изменять, удалять, переименовывать или переписывать архитектурные документы.

Разрешено:

- читать эти документы;
- анализировать их;
- использовать их при разработке.

Запрещено:

- изменять их;
- удалять их;
- переименовывать их;
- сокращать их;
- переписывать;
- добавлять в них новые архитектурные решения.

Если реализация требует изменения утверждённой архитектуры:

1. останови соответствующую часть работы;
2. опиши обнаруженное противоречие;
3. укажи техническую причину;
4. предложи варианты решения;
5. не изменяй архитектурные документы самостоятельно.

---

## 4. Если код противоречит архитектуре

Если существующий код противоречит архитектурным документам:

**изменяй код, а не архитектуру.**

Не сохраняй неправильную реализацию только потому, что она уже существует.

Перед удалением существующего кода убедись, что:

- он действительно больше не нужен;
- его функции реализованы в новом коде;
- соответствующие тесты обновлены;
- удаление не ломает другие части проекта.

---

## 5. Не задавай повторно уже утверждённые вопросы

Не запрашивай повторное подтверждение решений, которые уже определены в:

- `CLAUDE.md`;
- `docs/architecture/`.

Если техническая деталь не определена, выбирай наиболее простое, надёжное и совместимое с архитектурой решение.

Если решение способно изменить архитектуру — остановись и сообщи об этом.

---

## 6. Не создавать монолит

Не создавай огромные файлы с большим количеством независимой логики.

Каждый модуль должен иметь одну понятную ответственность.

Не создавать, например:

- один файл со всеми агрегаторами;
- один файл со всей логикой Scanner;
- один файл со всей Telegram-логикой;
- один файл со всей работой SQLite.

Разделяй:

- models;
- services;
- adapters;
- repositories;
- schedulers;
- calculators;
- workers;
- handlers.

---

## 7. Core не должен знать детали агрегаторов

Core не должен содержать aggregator-specific API logic.

Не создавать конструкции типа:

`if aggregator == "1inch"`

для реализации API-специфичного поведения.

Конкретная логика агрегатора должна находиться внутри соответствующего Adapter.

---

## 8. Aggregator Adapters

Каждый агрегатор должен иметь собственный Adapter.

Текущие агрегаторы:

- 1inch;
- 0x;
- Velora;
- Uniswap.

Все Adapter'ы должны соответствовать общему интерфейсу.

Adapter отвечает за:

- формирование API requests;
- API communication;
- response parsing;
- normalization;
- route extraction;
- fee extraction;
- capabilities;
- health checks;
- aggregator-specific error handling.

---

## 9. Актуальная документация API

Перед реализацией или изменением любого production Adapter обязательно проверь актуальную официальную документацию соответствующего API.

Проверяй:

- endpoints;
- parameters;
- authentication;
- network IDs;
- supported networks;
- supported tokens;
- rate limits;
- response schema;
- routing model;
- fee model.

Не выдумывай API endpoints, параметры или response fields.

Если официальная документация изменилась, адаптируй конкретный Adapter.

Не меняй архитектуру Monik из-за особенностей API без отдельного решения.

---

## 10. Mock API

Mock API разрешены только для:

- unit tests;
- integration tests;
- deterministic tests;
- failure simulation.

Mock implementation не является production implementation.

Не заявляй, что production API работает, если реализован только mock.

---

## 11. Финансовая точность

Не использовать `float` для критических финансовых расчётов.

Использовать:

- integer для raw blockchain amounts;
- `Decimal` для денежных и процентных расчётов.

Не допускать потери precision.

Особенно внимательно относиться к:

- token amounts;
- prices;
- fees;
- gas;
- profit;
- ROI.

---

## 12. Неизвестные данные

Никогда не интерпретировать:

- API error;
- timeout;
- missing fee;
- unknown fee;
- missing gas;
- invalid route;
- malformed response

как:

- zero;
- zero fee;
- zero gas;
- valid quote.

Если необходимых данных недостаточно для безопасного подтверждения:

**не подтверждай возможность.**

---

## 13. Fixed Route

Level 2 обязан проверять маршрут, найденный Level 1.

Нельзя автоматически заменить найденный маршрут другим маршрутом только потому, что он стал выгоднее.

Если агрегатор не способен корректно воспроизвести или проверить фиксированный маршрут:

результат не должен считаться полностью подтверждённым.

---

## 14. Resource Manager

Все внешние API requests должны проходить через Resource Manager.

Нельзя обходить Resource Manager напрямую из:

- Level 1;
- Level 2;
- Maintenance;
- Telegram;
- других worker'ов.

Resource Manager контролирует:

- concurrency;
- rate limits;
- locks;
- priorities;
- retry;
- cooldown;
- circuit breaker.

---

## 15. Приоритеты

При конфликте за один и тот же ресурс:

Level 2
>
Level 1

Внутри Level 1:

готовая SELL-проверка
>
незавершённая BUY-проверка.

Maintenance имеет более низкий приоритет.

Если операции используют разные ресурсы, они должны иметь возможность выполняться параллельно.

---

## 16. Level 1

Level 1:

1. получает BUY quotes;
2. определяет MAX BUY;
3. запускает SELL;
4. оценивает комбинации;
5. применяет threshold;
6. создаёт Opportunity.

Если BUY одного токена полностью завершён, его SELL не должен ждать завершения BUY других токенов.

---

## 17. Level 2

Level 2:

- получает Opportunity;
- использует настроенные суммы;
- использует тот же route;
- получает свежие quotes;
- получает необходимые комиссии;
- учитывает gas;
- рассчитывает net profit;
- определяет confirmation status.

Level 2 не должен самостоятельно искать новый маршрут.

---

## 18. Level 2 concurrency

Default:

`20`

Никогда не превышай установленный пользователем `max_parallel`.

Количество логических Level 2 Jobs должно быть отделено от количества resource locks.

---

## 19. Deduplication

Если одинаковые Level 2 workflows должны выполняться одновременно, объединяй их.

Не запускай несколько одинаковых Level 2 workflows одновременно.

После завершения предыдущего workflow повторное обнаружение той же возможности может создать новый K-ID.

---

## 20. ID

Level 1 использует:

`#V1234`

Level 2 использует:

`#K1234`

Это разные пространства идентификаторов.

Не меняй эту систему без отдельного архитектурного решения.

---

## 21. Capability Registry

Capability Registry должен хранить информацию о:

- network support;
- token support;
- BUY support;
- SELL support;
- routing support;
- fee capabilities;
- fixed-route support.

Не выполняй эти проверки перед каждым scan.

Они выполняются:

- при startup;
- или во время scheduled maintenance.

---

## 22. Maintenance

Поддерживать:

`startup`

и:

`daily`

с:

- `interval_days`;
- `time`.

Maintenance может выполнять:

- capability checks;
- token support checks;
- network checks;
- aggregator health checks;
- fee discovery/update;
- cleanup.

Maintenance использует тот же Resource Manager.

---

## 23. Fees

Fee system должна быть отделена от основной логики Scanner.

Adapter извлекает raw fee information.

Fee Policy нормализует и классифицирует её.

Unknown fee:

`UNKNOWN`

никогда не означает:

`0`.

Архитектура должна позволять изменить правила комиссий конкретного агрегатора без переписывания Scanner.

---

## 24. Fee optimization

Не получай комиссии заново при каждом scan, если это не требуется.

Используй:

- startup fee discovery;
- scheduled fee discovery;
- grouping;
- batching;

где это поддерживается API.

---

## 25. Calculator

Profit Calculator должен рассчитывать:

- gross;
- fees;
- gas;
- other costs;
- net profit;
- gross ROI;
- net ROI.

Используй точную арифметику.

---

## 26. Confirmation

Для каждой суммы поддерживаются:

- CONFIRMED;
- UNCONFIRMED;
- PARTIAL.

Если хотя бы одна сумма подтверждена, Opportunity может быть подтверждённой в соответствии с утверждённой логикой.

PARTIAL нельзя автоматически считать CONFIRMED.

---

## 27. Confirmation Rate

Использовать:

CONFIRMED
/
(CONFIRMED + UNCONFIRMED)
× 100

PARTIAL исключается.

Если отсутствуют CONFIRMED и UNCONFIRMED результаты:

`N/A`.

---

## 28. SQLite

SQLite является source of truth для recoverable state.

Хранить необходимые:

- Level 1 states;
- Level 2 jobs;
- Opportunities;
- attempts;
- notification queue;
- configuration versions;
- history.

Не хранить бесконечно все raw API responses.

Использовать migrations.

---

## 29. Atomic operations

Создание Opportunity и необходимого Level 2 Job должно быть атомарным.

Не допускать состояния:

Opportunity существует,
но необходимый Level 2 Job потерян.

---

## 30. Recovery

После запуска:

1. загрузить configuration;
2. открыть SQLite;
3. проверить integrity;
4. выполнить migrations;
5. восстановить незавершённое состояние;
6. инициализировать adapters;
7. инициализировать Resource Manager;
8. инициализировать Scheduler;
9. инициализировать Telegram;
10. запустить workers.

Если Level 2 был RUNNING во время аварии:

старый attempt становится INTERRUPTED.

Новый attempt должен начать проверку заново.

Старые quotes не использовать как свежие.

Старые runtime locks не восстанавливать.

---

## 31. Error Handling

Использовать категории:

- Temporary;
- Permanent;
- Data;
- System.

Temporary errors могут повторяться ограниченное число раз.

Permanent errors не должны бесконечно повторяться.

Data errors не должны превращаться в валидные quotes.

System errors должны передаваться соответствующей подсистеме Supervisor/Recovery.

---

## 32. Retry

Default:

`max_attempts = 3`

Использовать:

- exponential backoff;
- jitter.

Для HTTP 429 учитывать `Retry-After`, если он предоставлен.

Не использовать бесконечные retries.

---

## 33. Circuit Breaker

Использовать состояния:

`CLOSED`

`OPEN`

`HALF_OPEN`

Temporary outage не означает unsupported capability.

Circuit Breaker не должен изменять Capability Registry.

---

## 34. Supervisor

Supervisor контролирует:

- Level 1;
- Level 2;
- Resource Manager;
- Telegram;
- Maintenance.

При падении некритического worker попытаться восстановить именно его.

Критическая ошибка persistence должна переводить систему в SAFE_STOP.

---

## 35. Telegram

Telegram не должен блокировать Scanner.

Каждое Opportunity notification должно:

- показывать Level 2 ID сверху;
- содержать необходимую информацию;
- содержать кнопку `об`.

Кнопка `об` должна присутствовать в каждом Opportunity notification.

Кнопка не должна делать новый API request.

---

## 36. Telegram commands

Поддерживать:

`/details K1234`

`/level2`

`/status`

`/stats`

---

## 37. Telegram ordering

Уже сформированные уведомления отправлять в порядке их формирования.

Не сортировать их по:

- priority;
- profit;
- amount;
- aggregator.

Использовать:

`created_at`

и внутренний sequence number.

---

## 38. Telegram modes

User configuration должна поддерживать notification modes:

`A`

и:

`B`.

Mode влияет только на правила отправки Telegram notifications.

Mode не должен изменять алгоритмы Level 1/Level 2.

Если API не позволяет реализовать требование буквально, не симулируй его.

Claude Code не изменяет этот контракт самостоятельно.

## 56. Monik — одна программа, версии являются её состояниями

Программа называется **Monik**.

Обозначения вида `3.0`, `3.1`, `3.2`, `3.3`, а также имена каталогов и веток
(`Monik_3.2`, `monik-3.3`, `monik_3.3`) — технические обозначения конкретных
состояний и релизов одной и той же программы, а не разные продукты.

Из этого следует:

- правила, знания и требования не привязываются к номеру версии;
- всё, что записано в `CLAUDE.md`, действует для любого состояния Monik;
- переход на новую версию не отменяет накопленные правила и подтверждённые знания;
- формулировки вида «в 3.2 делаем так, а в 3.3 иначе» недопустимы в постоянных
  правилах: если поведение действительно различается, это различие описывается в
  `PROJECT_MEMORY.md` как состояние, а не как правило.

## 57. Постоянная память проекта

Используются три уровня постоянного контекста. У каждого своё назначение,
дублировать содержимое между ними не нужно.

**1. `CLAUDE.md`** — постоянные правила работы над Monik. Действуют всегда и для
любой версии. Меняются редко и только по решению пользователя.

**2. `PROJECT_MEMORY.md`** — переносимая проектная память: фактическое состояние
Monik, история изменений, обнаруженные и исправленные проблемы, подтверждения,
нерешённые вопросы, следующий шаг. Хранится в Git и переносится вместе с
исходным кодом на другой VPS и в другое состояние Monik.

**3. Auto Memory** — локальная рабочая память Claude Code для динамических
наблюдений: результаты диагностики, особенности окружения, повторяющиеся
проблемы и способы их выявления, предпочтения процесса разработки.

Правила ведения:

- знание, которое обязано пережить перенос проекта на другой VPS, помещается в
  `CLAUDE.md` или `PROJECT_MEMORY.md`, а не только в Auto Memory;
- в `PROJECT_MEMORY.md` подтверждённые факты и гипотезы разделяются явно; у
  каждого факта указывается, чем он подтверждён;
- полезная история в `PROJECT_MEMORY.md` не стирается: обновляется текущее
  состояние, а устаревшее переносится в историю;
- проверенное считается проверенным, а непроверенное — непроверенным; тест,
  прошедший на mock, не подтверждает работу production;
- при старте сессии порядок чтения: `CLAUDE.md` → `PROJECT_MEMORY.md` →
  `git log` → `docs/architecture/` → код.

## 58. Безопасная работа с production

Monik может быть развёрнут и работать на сервере как служба, в отдельном каталоге,
со своей боевой конфигурацией и своей базой данных. Каталог разработки и каталог
развёртывания — разные вещи. Конкретные пути текущего развёртывания фиксируются в
`PROJECT_MEMORY.md`.

Запрещено без явного указания пользователя:

- запускать, останавливать, перезапускать, включать или отключать службу Monik;
- изменять боевую конфигурацию и файлы службы;
- изменять, перемещать, перезаписывать или удалять боевую базу данных;
- переносить базу или конфигурацию между состояниями Monik.

Обязательно:

- перед любым действием с боевой базой убедиться, что есть резервная копия;
- боевую конфигурацию переносить как есть, не подменяя её примером
  `config.example.yaml`;
- секреты читать только из переменных окружения и файла окружения службы; не
  копировать их в репозиторий, отчёты, логи, память проекта и сообщения;
- содержимое боевой базы не выгружать и не копировать за пределы сервера;
- диагностику production вести по логам службы и по её собственным командам
  состояния, а не изменением боевого состояния.

Различие окружений существенно: проверки, обязательные в `production`, могут не
выполняться в `development`. Успешный запуск в `development` не доказывает
работоспособность в `production`.
